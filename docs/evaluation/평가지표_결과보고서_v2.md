## 2. 9.1 대화(LLM/RAG) 레이어

### 2.1 RAGAS 4지표 — 직무지식 골든셋 40건

| 지표 | 주입건(n=35) | 전체(n=40) | 등급 |
|---|---:|---:|:--:|
| Faithfulness | **0.967** | 0.846 | 🟢 |
| Answer Relevancy | **1.000** | 1.000 | 🟢 |
| Context Precision | 0.689 | 0.603 | 🟡 |
| Context Precision (AP) | **1.000** | 0.875 | 🟢 |
| Context Recall | **1.000** | 0.875 | 🟢 |

**가이드의 RAG Triad 대응**

가이드는 3대 축을 `Faithfulness · Answer Relevance · Context Relevance`로 부른다.
셋째 축은 우리 표에서 **Context Precision/Recall** 두 지표로 나뉜다.

| 가이드 축 | 본 문서 지표 | 값 |
|---|---|---:|
| Faithfulness | Faithfulness | **0.967** |
| Answer Relevance | Answer Relevancy | **1.000** |
| **Context Relevance** | Context Precision (AP) + Context Recall | **1.000** · **1.000** |

- **지식 주입률 87.5%** (35/40) · **정답 청크 주입률 77.5%** (31/40)
- Context Precision이 낮은 것은 결함이 아니다. 주입 5청크 중 정답 단계 1개만 "유용"으로
  세므로 상한이 구조적으로 1/5이다. **순위를 반영한 AP가 1.000**이라는 것이 실질 신호다.
- 전체 열이 낮은 이유는 주입 0건(5건)이 0점으로 들어가기 때문이다.

### 2.4 G-Eval — **두 개의 심판을 갈라 읽어야 한다**

가이드의 G-Eval을 우리는 두 군데에 쓴다. **재현성이 정반대라 한 줄로 묶으면 오독된다.**

| | 무엇을 채점하나 | 점수 | 재현성 | 등급 |
|---|---|---:|---:|:--:|
| **A. 대화 심판** | 상담 응답의 4차원 | **4.74~4.95** | sd **0.00~0.07** | 🟢 |
| **B. 미션 채점기** | 사용자 과제 답안의 총점 | — | sd **1.73** | 🔴 |

**A는 측정 도구**(사용자와 무관)이고 **B는 운영 코드**(사용자가 점수를 받는다)다.
"G-Eval 재현성 🔴"이라고만 적으면 **A까지 못 믿는 것으로 읽힌다.**

#### A. 대화 심판 — 상담 응답 4차원 (김태수 측정, n=40 · 3회 재채점)

| 차원 | 점수 | 재현성(sd) | 등급 |
|---|---:|---:|:--:|
| 자연스러움 | **4.88** / 5 | 0.05 | 🟢 |
| 적절성 | **4.80** / 5 | 0.04 | 🟢 |
| 도움됨 | **4.74** / 5 | 0.07 | 🟢 |
| 안전성 | **4.95** / 5 | **0.00** | 🟢 |

DB에 남은 **실제 상담 턴** 40건이 대상이며, 휴먼 평가와 **같은 차원·같은 앵커**를 쓴다
(사람 점수와 나란히 놓고 대조하기 위해서다). 안전성은 2점 이하가 **0건**이다.

⚠️ **G-Eval 수치가 두 벌 있으니 표본을 확인하고 인용할 것.**

| 차원 | ① 독립 표본 40건 | ② 휴먼평가 시트 40건 |
|---|---:|---:|
| 자연스러움 | 4.88 | 4.85 |
| 적절성 | 4.80 | 4.83 |
| 도움됨 | 4.74 | 4.74 |
| 안전성 | **4.95** | **5.00** |

②는 **사람이 채점한 그 40건을 심판이 다시 채점한 것**이라(§5.3의 대조용) 표본이 다르다.
같은 표본이면 안전성 sd 0.00과 모순되므로, **한 표에 섞어 쓰면 안 된다.**
위 A표의 값은 ①이다.

**평균 sd 0.07 이하 = 같은 답안에 사실상 같은 점수를 다시 낸다.** 자동 회귀 지표로 쓸 수 있다.
심판은 측정 도구이므로 `temperature=0`이 더 적절하지만, 현재 값(0.3)에서 이미 sd 0.07이라
바꾸는 실익이 작다.

#### B. 미션 채점기 — 과제 답안 채점 (n=45)

이 심판이 채점기를 감사한 결과는 양호하다.

| 축 | 평균 | sd |
|---|---:|---:|
| 채점기준 실제 적용 | 4.89 | 0.53 |
| 피드백 구체적 근거 | 4.78 | 0.60 |
| 제공자료 근거 확인 | **5.00** | 0.00 |
| **3축 통합** | **4.89** | (≥4 비율 96%) |

**등급 분리도** — 상 100.0 / 중 61.2 / 하 6.1 (평균 상–하 격차 **93.9점**).
같은 회차 삼중 비교 15조에서 순서 위반 **0건**, 교차회차 225쌍에서도 역전 **0건**.

🔴 **그런데 채점기 자체의 재현성이 낮다.** 동일 답안 5회 재채점 시 평균 sd **1.73점**,
최대 범위 15점, **9답안 중 2개는 합/불이 갈렸다.** 경계 점수대(67~73)에서 발생한다.

이건 **측정 문제가 아니라 제품 문제다** — 같은 답안을 낸 사용자가 다른 결과를 받는다.
`evaluate_task`가 `chat_json` 기본 온도(0.3)를 그대로 쓰고 있어, **온도 0 고정 + 합격선
근처(65~75점)만 3회 채점해 중앙값으로 판정**하면 비용을 크게 늘리지 않고 줄일 수 있다.
(정답이 있는 선택형·순서형은 지금처럼 코드로 채점한다.)

### 3.2 프롬프트 수정 — 4건 적용 완료 (2026-07-29)

아래 1·2·3·5는 **적용했고 재측정으로 효과를 확인**했다(§2.5). 4는 보류했다.

1. **질문 스태킹** — 24행 "한 번에 질문 하나만"이 이미 있는데 안 지켜진다.
   물음표 문장 + `~해 주세요`류 요청문을 **합쳐 1개**로 계수 기준까지 명시.
2. **수신 신호** — 25행을 감사·맞장구·최소 반응 턴까지 확장해
   "직전 발화를 받는 한마디를 반드시 앞에 둔다"로 명시. 인테이크 3지선다는 세션당 1회로 억제.
3. **입력 인용** — "사용자가 쓴 표현 1~2개를 그대로 되짚은 뒤 질문한다(총칭 요약으로 대체 금지)".
4. **위기 응대(D31)** — 위기 라우팅 자체는 적절했고 번호(109 / 1577-0199)도 실재해 환각이 없다.
   다만 열린 질문 없이 닫아 회피처럼 읽힌다. 위기 섹션에 **진로와 무관한 열린 질문 1개**를 허용.
   ⚠️ **핫라인 제거 방향의 수정은 금지.**
5. **호칭(D24)** — 1:1 상담인데 "여러분"이라는 방송형 복수 호칭 사용. 2인칭 단수 존대로 통일.

⚠️ 워밍업(`/api/avatar/warmup`)은 **9.1초** 걸린다(콜드스타트). 시연 직전에 한 번 쳐둘 것.

### 4.2 TTFB 🟡 — 커넥션 유휴 만료를 고쳐 993ms 줄였다

```
(수정 전) TTFB 2,591ms = 임베딩 1,262ms + LLM 첫 토큰 1,330ms
(수정 후) TTFB 1,550ms = 임베딩   343ms + LLM 첫 토큰 1,207ms   ← 21턴
```

**원인은 RAG 자체가 아니라 HTTP 커넥션이었다.** httpx 기본 `keepalive_expiry`가 **5초**라,
상담 턴 사이(사용자가 읽고 타이핑하는 20~40초)마다 커넥션이 닫히고 다음 턴에서 TLS를
다시 맺었다. **모든 턴이 예외 없이 재수립 비용을 물고 있었다.**

VM 실측 — 동일 쿼리·동일 프로세스에서 **호출 간격만** 바꿨다:

| 호출 간격 | 임베딩 지연 |
|---:|---:|
| 3초 | **330ms** ← 커넥션 재사용 |
| 10초 | **1,215ms** ← 여기서 점프 (**+885ms**) |
| 20초 | 1,264ms |
| 40초 | 1,271ms ← 이후 평평 = 재수립 비용은 상수 |

실서버 임베딩 p50 1,262ms가 정확히 이 값이었다.

**조치**: `llm_keepalive_expiry_s`(기본 300초)를 추가해 genai 클라이언트에
`async_client_args`로 전달. 주기적 더미 핑보다 낫다 — 추가 호출·비용·쿼터 소모가 없다.

**배포 후 실측(21턴)**: 임베딩 p50 **343ms** · TTFB p50 **1,550ms** · p95 2,569ms.
목표 1.5초까지 50ms 남았다.
(p95의 1,831ms는 컨테이너 기동 후 최초 1회 TLS 수립 비용으로, 표본이 쌓이면 희석된다.)

**기각한 가설** — 전부 실측으로 반증했고, 그 과정이 답으로 이어졌다:

| 가설 | 반증 |
|---|---|
| 재시도·할당량 | 재시도 경고 로그 0건 |
| 오래된 클라이언트 | 컨테이너 재시작해도 동일(1,425/1,257/1,270ms) |
| 쿼리 내용·길이 | 2글자 더미 쿼리도 동일하게 느림 |
| 아바타 릴레이 경합 | 아바타 ON/OFF 차이 +11ms |

⚠️ 2번째 가설(커넥션 재수립)은 **방향이 맞았는데 3초 간격으로만 테스트해 오판**했다.
실제 만료가 5초라 3초는 통과했던 것이다. 간격을 3·10·20·40초로 넓혀 재고 나서야 보였다.
**임계값을 찾을 땐 후보 구간을 넓게 훑을 것.**

남은 TTFB의 대부분은 이제 LLM 첫 토큰(~1,207ms, 78%)이다.

#### 남은 LLM 구간은 줄일 수 있는가 — 프롬프트 크기 실험

"프롬프트 15KB가 무거워서 느린 것 아니냐"를 확인하려고, **같은 모델·같은 VM에서
system 프롬프트 크기만 바꿔** 첫 토큰을 쟀다. 실사용과 같은 **30초 간격**, 두 조건을
**교대로** 실행해 시간대 편향을 없앴다(각 8회).

| 조건 | min | p50 | p95 |
|---|---:|---:|---:|
| 최소 프롬프트 (3토큰) | **973ms** | 1,225ms | 1,516ms |
| 실제 프롬프트 (2,869토큰) | 1,204ms | **1,306ms** | 1,835ms |

같은 회차끼리 짝지은 차이: `+184 −21 −270 +54 +579 +296 +156 +301`
→ 평균 **+160ms** · 중앙 +170ms · 8쌍 중 6쌍 양수 · **t=1.80 (기준 2.36) → 유의성 미달**

**결론**: 프롬프트를 3토큰까지 줄여도 p50 **1,225ms**, 최저 973ms가 나온다.
LLM 구간의 대부분은 **모델 고유 지연**이다. 프롬프트 기여분은 +160ms 부근으로 보이나
n=8에서 통계적으로 확정되지 않으므로 **추정으로만 적는다.**

격리 측정(실제 프롬프트 p50 1,306ms)과 실사용 21턴 역산값(1,550−343=1,207ms)이
**100ms 안에서 일치**해 두 측정 모두 신뢰할 수 있다.

⚠️ **이 실험은 1초 간격으로 먼저 했다가 폐기했다.** 연속 호출에서는 5~11초 스파이크가
섞여 편차가 지배해 프롬프트 효과를 볼 수 없었다(같은 조건 min 1,081 / max 11,223ms).
**측정 간격을 실사용과 맞추지 않으면 그 자체가 교란 변수가 된다.**

→ 프롬프트를 통째로 지워도 TTFB는 ~1,390ms다. 목표 안에 들어오지만 Faithfulness 0.967·
안전성 15/15를 잃는 거래라 권하지 않는다. 실질적 개선 경로는 **RAG를 임계 경로에서
빼는 것**(선검색·병렬화·캐시)이며 구조 변경이라 시연 후 과제다.

#### 모델을 바꾸면 해결되는가 — `gemini-3.5-flash` 재검증

"더 빠른 모델을 쓰면 되지 않느냐"에 답하기 위해 **직전 버전 3.5-flash를 실사용 조건으로
다시 쟀다**(30초 간격 · 모델 교대 · 각 8회). 토큰·비용은 타이밍과 무관하므로 연속 10회씩
별도 측정했다.

| 축 | 3.5-flash | 3.6-flash | 판정 |
|---|---:|---:|---|
| 첫 토큰 p50 | 1,239ms | 1,261ms | 차이 22ms · **t=−0.25 → 구분 불가** |
| **입력 토큰** | 4,817 | 4,817 | **10/10 회차 완전 일치** (토크나이저 동일) |
| 출력 토큰 | 105 | 104 | +0.8토큰 · t=0.05 → 차이 없음 |
| **1콜 비용** | **$0.00801** | **$0.00801** | 차이 **0.008원** |

**되돌릴 근거가 하나도 나오지 않았다.** 속도·토큰·비용 어느 축에서도 3.5의 우위가
관측되지 않는다(첫 토큰 95% 신뢰구간 −134~+108ms로, 어느 방향이든 유의한 차이 없음).

반대로 **3.6을 유지할 근거는 셋이다.**

1. **전체 응답이 13.5% 빠르다** — 2026-07-23 이관 검증(n=10 페어드) 결과이며, 이번에
   재측정한 첫 토큰과 달리 **끝까지 받는 시간**을 잰 값이다. 되돌리면 사용자가 문장을
   다 받는 데 걸리는 시간이 늘어난다. 품질도 당시 차이 없음이 확인됐다(t=+0.77).
2. **본 보고서의 모든 품질 수치가 3.6 기준으로 확정돼 있다** — Faithfulness 0.967 ·
   위험 6종 15/15 · 일상·엣지 94.4% · G-Eval 4.89. 모델을 바꾸면 **이 전부가 무효**가 되고
   골든셋 145건을 다시 돌려야 한다. 그중 위험 15건은 릴리스 블로커다.
3. **`thinking_budget=0` 지원이 검증돼 있다** — 이 파라미터를 거부하는 모델 계열이 있고
   (gemini-2.5-pro는 400으로 상담이 죽는다), 상담 경로가 이 값을 하드코딩한다.

> **결론**: 모델 교체로 얻는 것은 측정되지 않았고, 잃는 것은 확정적이다. **3.6 유지.**

#### TTFB 하한은 모델이 아니라 계열 특성이다

세 조건에서 첫 토큰 p50이 모두 **1,200ms 부근**으로 모인다.

| 조건 | 첫 토큰 p50 |
|---|---:|
| 3.6-flash · 실제 프롬프트(2,869토큰) | 1,261~1,306ms |
| 3.5-flash · 실제 프롬프트 | 1,239ms |
| 3.6-flash · **최소 프롬프트(3토큰)** | **1,225ms** |

**프롬프트를 3토큰까지 줄여도, 모델을 직전 버전으로 바꿔도 1,200ms 아래로 내려가지 않는다.**
목표 1.5초 대비 50ms 초과는 **모델 선택이나 프롬프트 크기의 문제가 아니라 flash 계열의
공통 하한**이며, 여기에 RAG 검색 343ms가 직렬로 얹혀 1,550ms가 된다.

→ 남은 개선 경로는 **RAG를 임계 경로에서 빼는 것** 하나다.

### 4.4 임베딩 타임아웃 장애 — 실서버 RAG가 죽어 있었다 (당일 발견·복구)

**증상**: VM 상담 11턴에서 RAG 실행 8건이 **8건 전부 타임아웃 → 지식 주입률 0%**.
실서버 상담이 직무 지식 없이 답하고 있었다.

**원인**: 컷을 2.0s → **1.0s로 낮춘 것**(같은 날 오전 내 변경). 근거로 삼은
"임베딩 p50 365ms · p90 409ms"는 **로컬 단독 벤치**였고, 프로덕션에는 해당하지 않았다.

| 조건 | p50 | max | 1.0s 초과 |
|---|---:|---:|---:|
| VM · 단독 측정 | 606ms | 1,320ms | 2/10 |
| **VM · 실제 요청 중** | **1,262ms** | **1,622ms** | **8/8** |

단독으로 재면 606ms, 요청 처리 중엔 1,262ms로 **2배**가 된다. 컷 1.0s가 분포 바로 아래에
앉아 전건이 걸렸다. **단독 벤치로 프로덕션 임계값을 정하면 안 된다**는 것이 이 사건의 교훈이다.

**조치**(PR #280):
- 기본값 2.0s 복구 + `settings.rag_embed_timeout_s`로 설정화 → `.env`로 재배포 없이 조정
- `[RAG-EMBED] ms=... ok=0/1` 실측 로그 추가 → 이전엔 컷 값만 찍혀 **실제 지연을 알 수 없었다**
- `log_report.py`가 지식 주입 0건이면 "RAG 미동작" 경고를 띄우도록

**복구 확인**: 임베딩 8/8 성공 · 타임아웃 0% · max 1,622ms(컷 2.0s 대비 여유 19%).

### 4.5 Task Completion — 백분율로 보고하지 않는다

**이 절의 이전 판(11.5% / 48.9% 병기)은 폐기한다.** 담당(김태수)이 별도 검증에서
**비율 자체를 쓰지 않는 쪽**으로 정리했고, 그 판단이 옳다 —
원본: [완주검증_결과.md](완주검증_결과.md)

| 항목 | 결과 |
|---|---|
| 진행 불가 지점 (정적·서비스 계층 검사) | **0건** |
| 자동 완주 경로 검증 | **8/8 성공** (kts-03 · sns-01 각 4판) |
| 미니게임 실플레이 | 완주 기록으로 확인 |
| 실사용자 과업 완수율 | **서비스 오픈 후 측정** |

**왜 비율을 쓰지 않는가**: 우리 세션은 전량 팀·데모 계정의 개발 기록이라, 비율을 내면
사용자 행동이 아니라 **개발 패턴**을 재게 된다. 또한 자동 실행에는 이탈이라는 개념이
없어 무엇을 해도 100%가 나오므로 "완주율 100%"도 지표가 되지 못한다.

그래서 질문을 **"사용자가 나갔는가"에서 "시스템이 막았는가"로** 바꿔 측정했다.
이탈은 사람이 있어야 재지만, 막히는 지점은 지금도 찾을 수 있다.

**PPT 문구는 다음을 그대로 쓴다** (백분율 금지):

```
진행 불가 지점        0건
자동 완주 경로        8/8 성공
미니게임 실플레이      완주 확인
실사용자 과업 완수율   서비스 오픈 후 측정
```

#### 분모가 오염된 구조적 원인 (별개로 남는 문제)

세션 576건 중 **441건(77%)이 대화 0턴**이다. 시나리오 화면이 **진입 즉시 세션을 만들고**
([ScenarioGamePage.tsx:1410](../../apps/web/src/pages/ScenarioGamePage.tsx:1410)), 이어받기 기억을
`sessionStorage`에 두어 **탭을 닫으면 유실**되기 때문이다(연속 생성 간격 34%가 10초 이내,
시나리오 `ms-06` 하나에 237건 집중).

실사용자 데이터를 받기 전에 **세션 생성 시점을 첫 상호작용으로 옮겨야** 오픈 후 측정이
의미를 갖는다. 또한 `aborted`는 **포기 버튼을 누른 건수**일 뿐이라 이탈률로 읽으면 안 된다.

### 4.6 FPS 🟡 — 렌더링은 무손실, 상한은 소스 스펙

**브라우저 실측**(`requestVideoFrameCallback`, 표본 100건):

| 항목 | 값 |
|---|---:|
| 실표시 FPS p50 | **25.0** |
| p05 | 20.0 |
| max | 26.0 |
| 서버 목표(target) | 25 |

**실표시 = 목표 = 25.0 → 재생 단계의 프레임 손실이 없다.** `max 26.0`이 target 25를 넘는
것이 이 값이 목표치를 그대로 베낀 게 아니라 **독립 실측**임을 보여준다.

→ 가이드 목표 30fps 미달은 **우리 파이프라인 문제가 아니라 MuseTalk 생성 FPS(25)가 상한**이다.
30fps로 올리려면 코랩 쪽 생성 설정을 바꿔야 하며 **아바타 담당 소관**이다.
p05 20.0은 하위 5% 구간의 경미한 드롭이다.

⚠️ 이 계측은 **기본 꺼져 있다** — `?debug=1` 또는 `localStorage['jobiverse-avatar-debug']='1'`
일 때만 비콘이 뜬다([AiAvatarStage.tsx:33](../../apps/web/src/components/conversation/AiAvatarStage.tsx:33)).
재측정 시 URL에 `?debug=1`을 붙일 것.

### 4.7 STT(Web Speech) 확정 지연 🟢 — 원시값을 그대로 쓰면 안 된다

브라우저 음성 입력 5건 실측(`[STT]` 비콘). **원시 p50은 3,576ms지만 이 값을 "인식 지연"으로
보고하면 틀린다** — 이 구간은 *첫 신호 → 확정*이라 **사용자가 말한 시간이 통째로 포함**된다.

발화 길이로 회귀하면 거의 완전히 설명된다:

```
ms = 114.2 × 글자수 + 1,058          (R² = 0.977, n=5)
     └ 발화 속도 ┘   └ 확정 오버헤드 ┘
```

| 성분 | 값 | 해석 |
|---|---:|---|
| 글자당 | 114ms (초당 8.8자) | 말하는 시간 |
| **고정 오버헤드** | **1,058ms** | **말이 끝난 뒤 인식기가 확정하기까지** |

→ 보고할 값은 **확정 오버헤드 ≈ 1.06초**다. 변동의 97.7%가 발화 길이로 설명되므로
원시 p50/p95는 "얼마나 길게 말했나"를 재는 것에 가깝다.

**인식 정확도**: 5문장 전건 정확 인식(발화자 확인). 말이 꼬인 구간까지 들린 그대로 옮겨
적었다 — 표본은 작지만 오인식은 관측되지 않았다.

⚠️ **개인정보**: `[STT]` 로그에 인식된 발화 원문이 남는다(실측에서 실명이 기록됨).
평가 증빙 목적의 의도된 동작이지만([sttTelemetry.ts:12](../../apps/web/src/lib/sttTelemetry.ts:12) 주석),
시연 중 참관인 발화도 그대로 쌓이므로 운영 전환 시 노출 범위를 재검토해야 한다.

### 4.8 TTS 경로 — provider에 따라 음성 출처가 다르다 🟡

백엔드 설정만 보면 `elevenlabs_api_key`·`avatar_voice_id_female`이 비어 있지만,
**현재 운영 경로(musetalk)에서는 무관하다.** 릴레이가 텍스트를 그대로 코랩에 넘기고
**코랩이 TTS까지 수행**하기 때문이다([avatar/service.py:722](../../services/api/app/domains/avatar/service.py:722) 주석).
실사용 확인 결과 ElevenLabs 음성·여성 보이스 모두 정상 출력된다.

| provider | 음성 출처 | 실측 `[TTS]` 로그 |
|---|---|---|
| **musetalk** (현재) | **코랩** | 0건 — 백엔드 TTS 미사용 |
| fastapi / gradio (폴백) | 백엔드 `tts_service` | gtts 31건 |

⚠️ **폴백 시 음질이 급락한다.** 코랩이 끊겨 fastapi로 폴백되면 백엔드 TTS가 동작하는데,
`elevenlabs_api_key`가 비어 있어 **gTTS 기계음**이 나간다. 오늘 아바타 다운 시 실제로 그랬다
(합성 31건 전부 gtts). 시연 중 코랩이 끊기면 같은 일이 벌어지므로, 안전망으로
백엔드에도 ElevenLabs 키를 넣어두는 편이 좋다.

**9.2(CER·MCD)는 실제로 코랩 출력 음성을 대상으로 측정됐다**(§2.6) — 백엔드 TTS 설정을
보고 판단하면 안 된다는 점이 이 사례로 확인됐다. 백엔드 `elevenlabs_api_key`가 비어 있어도
운영 경로의 음성 품질은 CER 0.4~0.7%로 정상이다.

### 5.1 골든셋 구성 — 가이드 목표 비율 대비

| 카테고리 | 목표 | 현재 | 비율 | 출처 |
|---|---:|---:|---:|---|
| 일상 | 40% | 60 | 41.4% | 실서버 발화 **100%** |
| 전문 | 30% | 40 | 27.6% | 청크 기반 생성 |
| 엣지 | 20% | 30 | 20.7% | 실발화 16 + 변형 2 + 합성 12 |
| 위험 | 10% | 15 | 10.3% | **전량 합성** |
| **계** | | **145** | | |

일상·엣지는 실서버 고유 유저 발화 **473건**(2026-07-14~28)을 전수 분류해 선별했다.
**위험이 전량 합성인 것은 불가피하다** — 실서버 발화 473건에 위험 신호는 사실상 없었다.

**항목 구성** — 가이드는 `질문 + 기대 답변 + 근거 문서` 쌍을 요구한다. 파트별로 형태가 다르다.

| 파트 | 질문 | 기대 답변 | 근거 문서 |
|---|---|---|---|
| 전문 40 | `q` | `ground_truth` (모범답변) | `gt_chunk_id` + `chunk_text` |
| 일상 60 · 엣지 30 | `q` | `pass_criteria` / `fail_criteria` | — (지식 불필요한 턴) |
| 위험 15 | `q` | 카테고리별 `pass_criteria` | — |

전문 파트는 **청크가 곧 정답**이라 Recall·MRR을 LLM 없이 결정적으로 잴 수 있다.
일상·엣지·위험은 정답 문서가 존재하지 않는 발화(인사·잡담·이상입력·위기)라
**모범답변 대신 판정 기준**을 둔다 — LLM 심판이든 사람이든 같은 기준으로 채점한다.

### 5.3 휴먼 평가 — 3인 완료 🟢

원본: [휴먼평가_결과.md](휴먼평가_결과.md) · 설계: [휴먼평가_설계.md](휴먼평가_설계.md)

평가자 **3인** · 표본 40건(시드 42) · 상의 없이 독립 채점.

| 차원 | 사람 점수 | 평가자 간 일치도 | LLM 심판 | 차이 |
|---|---:|---:|---:|---:|
| 자연스러움 | **4.88** / 5 | 97.4% 🟢 | 4.85 | −0.03 |
| 적절성 | **4.87** / 5 | 95.7% 🟢 | 4.83 | −0.04 |
| 도움됨 | **4.70** / 5 | 89.7% 🟢 | 4.74 | +0.04 |
| 안전성 | **4.96** / 5 | 96.6% 🟢 | 5.00 | +0.04 |

**일치도가 네 차원 모두 🟢**(기준 80%)라 점수를 그대로 보고할 자격이 확보됐다.
일치도가 낮으면 평균은 의견 모음일 뿐이므로, 점수보다 이쪽을 먼저 본다.

#### 심판을 계속 써도 되는가 — 평균은 어긋나지 않는다

**평균 차이가 최대 0.04점**이다. 심판이 사람보다 후하지도 박하지도 않아, 자동 회귀
지표로 계속 쓸 근거가 된다.

#### 상관관계 — 산출했고, 가이드 기준을 충족하지 못한다

가이드는 G-Eval을 **"LLM-as-Judge (인간 평가와 상관관계 80%+)"**로 정의한다.
**평균 일치와 상관관계는 다르다** — 평균이 같아도 항목마다 엇갈릴 수 있다.

```
사람  5 5 4 5 3
심판  3 5 5 4 5     ← 평균은 둘 다 4.4, 상관관계는 음수
```

그래서 따로 계산했다(`human_eval_report.py`가 자동 산출).

| 차원 | Pearson | Spearman | 사람 점수 분산 | 가이드 80%+ |
|---|---:|---:|---:|---|
| 자연스러움 | 0.228 | 0.344 | 0.218 | ❌ |
| 적절성 | 0.092 | 0.242 | 0.233 | ❌ |
| 도움됨 | 0.433 | 0.398 | 0.414 | ❌ |
| 안전성 | 계산 불가 | 계산 불가 | 0.153 | — |

안전성은 심판이 40건 전부 5.00을 줘 **분산이 0이라 상관계수가 정의되지 않는다.**

**결론: "인간 평가와 상관관계 80%+"는 충족하지 못했다.** 그대로 보고한다.

##### 다만 이 수치로 "심판이 틀렸다"고 읽으면 안 된다

사람 점수 분산이 **0.15~0.41**뿐이다. 40건이 거의 전부 4.7~5.0에 몰려 있어(천장 효과)
남는 게 잡음이고, 이 구간에서는 상관계수가 **구조적으로** 낮게 나온다(범위 제한).

즉 지금 표본으로는 **상관이 높다고도 낮다고도 주장할 근거가 없다.** 말할 수 있는 것은
다음 둘뿐이다.

- 평균이 어긋나지 않는다 (차이 ≤ 0.04)
- ±1점 이내 일치율 90~100%

실제로 항목 단위로 **8건이 1.5점 이상 어긋났다**(아래 사각지대 2종).

##### 제대로 재려면

점수가 퍼지는 표본이 필요하다 — `edge_30`·`risk_15` 활용, 의도적 열화 응답 삽입,
표본 40 → 80건 확대. 셋 다 평가자 시간이 추가로 든다.
**오픈 전까지 못 하면 "미산출"이 아니라 "산출했으나 천장 효과로 해석 보류"로 적는다.**

#### 심판의 사각지대 2종 (항목 단위 8건)

| 방향 | 건수 | 유형 | 예 |
|---|---:|---|---|
| 심판이 **박함** | 6 | 되짚기·질문으로 시작하는 응답 | H034·H036·H040·H027 |
| 심판이 **후함** | 2 | 잡담 턴의 '도움됨' | H014 "이력서 훔쳐봤니?" · H009 "고마워요" |

심판은 "물은 것에 바로 답하지 않았다"로 감점했지만, 사람은 상담 맥락에서 되짚기를
자연스럽다고 봤다. 반대로 질문이 아닌 발화에는 "다음에 뭘 할지"가 없는데도 5점을 줬다.

**이 8건을 심판 앵커 수정 시 회귀 케이스로 쓴다.**

### 5.2 미해결 — 골든셋이 DB에 묶여 있다 🔴

`job_knowledge_40.json`의 `gt_chunk_id`(1035~1543)는 **DB 자동증가 PK**다.
코퍼스가 동일해도 **재시드하면 PK가 달라져 Recall이 0%로 나온다.**
이번에도 로컬 DB(id 1~564)에서 처음 돌렸을 때 Recall@1/@5가 0.0%였고,
`reclassify_golden.py`로 재생성한 뒤에야 정상값이 나왔다(질문 40/40·분류 40/40 동일, ID만 상이).

**제안**: `gt_chunk_id`와 별도로 **본문 해시나 (job_code, stage) 같은 안정 키**를 함께 저장해
어느 환경에서도 재현되게 한다. 지금은 평가 전에 `reclassify_golden.py`를 먼저 돌려야 한다.

## 7. 재현 방법

```bash
# 0) 골든셋을 현재 DB 기준으로 재생성 (PK 결합 회피 — 필수)
docker compose exec api python -m app.scripts.reclassify_golden --out /tmp/golden_local.json
```
