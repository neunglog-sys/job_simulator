### 3.2 프롬프트 수정안 (`data/prompts/avatar/system.md`)

1. **질문 스태킹** — 24행 "한 번에 질문 하나만"이 이미 있는데 안 지켜진다.
   물음표 문장 + `~해 주세요`류 요청문을 **합쳐 1개**로 계수 기준까지 명시.
2. **수신 신호** — 25행을 감사·맞장구·최소 반응 턴까지 확장해
   "직전 발화를 받는 한마디를 반드시 앞에 둔다"로 명시. 인테이크 3지선다는 세션당 1회로 억제.
3. **입력 인용** — "사용자가 쓴 표현 1~2개를 그대로 되짚은 뒤 질문한다(총칭 요약으로 대체 금지)".
4. **위기 응대(D31)** — 위기 라우팅 자체는 적절했고 번호(109 / 1577-0199)도 실재해 환각이 없다.
   다만 열린 질문 없이 닫아 회피처럼 읽힌다. 위기 섹션에 **진로와 무관한 열린 질문 1개**를 허용.
   ⚠️ **핫라인 제거 방향의 수정은 금지.**
5. **호칭(D24)** — 1:1 상담인데 "여러분"이라는 방송형 복수 호칭 사용. 2인칭 단수 존대로 통일.

### 3.3 골든셋 기준 결함 (제 실수)

- **문장 수 상한이 항목마다 2 / 2~3 / 4로 제각각**이라 같은 품질 응답이 항목에 따라 갈렸다
  (D13·D24는 80자 남짓인데 "3문장 이상 장문"으로 탈락, 동일 유형 D23은 통과).
  → 문장 수 기준을 **글자 수 + 질의 계수**로 대체해야 한다.
- **D31의 pass_criteria가 위기 대응과 충돌**한다. "무슨 일인지 질문 1개"를 필수로 걸면
  골든셋이 캐묻기를 보상하고 자원 안내를 벌하게 되어 **최적화 방향이 안전에 역행**한다.
  위기 항목에 안전 예외 조항이 반드시 필요하다.

### 4.2 TTFB 🔴 — 목표 1.5초를 못 맞춘다

```
TTFB 2,591ms  =  임베딩 1,262ms  +  LLM 첫 토큰 ~1,330ms
```

**절반이 임베딩이다.** RAG가 스트리밍 시작 전 직렬 구간이라 사용자가 그만큼 빈 화면을 본다.

근본 해결은 **RAG를 임계 경로에서 빼는 것**(선검색·병렬화·캐시)이며 구조 변경이라 시연 후 과제다.

스트리밍 조기 종료 1건은 토큰이 집계되지 않는다(`truncated=1`) — 실제 비용은 소폭 높다.

### 4.4 임베딩 타임아웃 장애 — 실서버 RAG가 죽어 있었다 (당일 발견·복구)

**증상**: VM 상담 11턴에서 RAG 실행 8건이 **8건 전부 타임아웃 → 지식 주입률 0%**.
실서버 상담이 직무 지식 없이 답하고 있었다.

**원인**: 컷을 2.0s → **1.0s로 낮춘 것**(같은 날 오전 내 변경). 근거로 삼은
"임베딩 p50 365ms · p90 409ms"는 **로컬 단독 벤치**였고, 프로덕션에는 해당하지 않았다.

| 조건 | p50 | max | 1.0s 초과 |
|---|---:|---:|---:|
| VM · 단독 측정 | 606ms | 1,320ms | 2/10 |
| **VM · 실제 요청 중** | **1,262ms** | **1,622ms** | **8/8** |

단독으로 재면 606ms, 요청 처리 중엔 1,262ms로 **2배**가 된다. 컷 1.0s가 분포 바로 아래에
앉아 전건이 걸렸다. **단독 벤치로 프로덕션 임계값을 정하면 안 된다**는 것이 이 사건의 교훈이다.

**조치**(PR #280):
- 기본값 2.0s 복구 + `settings.rag_embed_timeout_s`로 설정화 → `.env`로 재배포 없이 조정
- `[RAG-EMBED] ms=... ok=0/1` 실측 로그 추가 → 이전엔 컷 값만 찍혀 **실제 지연을 알 수 없었다**
- `log_report.py`가 지식 주입 0건이면 "RAG 미동작" 경고를 띄우도록

**복구 확인**: 임베딩 8/8 성공 · 타임아웃 0% · max 1,622ms(컷 2.0s 대비 여유 19%).

### 4.5 Task Completion Rate — 분모 정의

| 분모 | 완주율 |
|---|---:|
| 전체 세션 (가이드 산식) | 66/576 = **11.5%** |
| **시도 세션(대화 1턴 이상)** | 66/135 = **48.9%** |
| 최근 7일 | 35/167 = 21.0% |

전체 576건 중 **441건(77%)이 대화 0턴**이다. 시나리오 화면은 **진입 즉시 세션을 만들고**
([ScenarioGamePage.tsx:1410](../../apps/web/src/pages/ScenarioGamePage.tsx:1410)), 이어받기 기억을
`sessionStorage`에 두어 **탭을 닫으면 유실**된다. 개발 중 반복 진입이 그대로 분모에 쌓였다
(연속 생성 간격 34%가 10초 이내, 시나리오 `ms-06` 하나에 237건 집중).

→ **두 값을 병기**하고 정의를 명시할 것. `aborted`는 **포기 버튼을 누른 건수**일 뿐이므로
"중도 포기 0.2%"를 이탈률로 읽으면 안 된다 — 실제 이탈은 `active`에 숨어 있다.

### 4.6 FPS 🟡 — 렌더링은 무손실, 상한은 소스 스펙

**브라우저 실측**(`requestVideoFrameCallback`, 표본 100건):

| 항목 | 값 |
|---|---:|
| 실표시 FPS p50 | **25.0** |
| p05 | 20.0 |
| max | 26.0 |
| 서버 목표(target) | 25 |

**실표시 = 목표 = 25.0 → 재생 단계의 프레임 손실이 없다.** `max 26.0`이 target 25를 넘는
것이 이 값이 목표치를 그대로 베낀 게 아니라 **독립 실측**임을 보여준다.

→ 가이드 목표 30fps 미달은 **우리 파이프라인 문제가 아니라 MuseTalk 생성 FPS(25)가 상한**이다.
30fps로 올리려면 코랩 쪽 생성 설정을 바꿔야 하며 **아바타 담당 소관**이다.
p05 20.0은 하위 5% 구간의 경미한 드롭이다.

⚠️ 이 계측은 **기본 꺼져 있다** — `?debug=1` 또는 `localStorage['jobiverse-avatar-debug']='1'`
일 때만 비콘이 뜬다([AiAvatarStage.tsx:33](../../apps/web/src/components/conversation/AiAvatarStage.tsx:33)).
재측정 시 URL에 `?debug=1`을 붙일 것.

### 4.7 STT(Web Speech) 확정 지연 🟢 — 원시값을 그대로 쓰면 안 된다

브라우저 음성 입력 5건 실측(`[STT]` 비콘). **원시 p50은 3,576ms지만 이 값을 "인식 지연"으로
보고하면 틀린다** — 이 구간은 *첫 신호 → 확정*이라 **사용자가 말한 시간이 통째로 포함**된다.

발화 길이로 회귀하면 거의 완전히 설명된다:

```
ms = 114.2 × 글자수 + 1,058          (R² = 0.977, n=5)
     └ 발화 속도 ┘   └ 확정 오버헤드 ┘
```

| 성분 | 값 | 해석 |
|---|---:|---|
| 글자당 | 114ms (초당 8.8자) | 말하는 시간 |
| **고정 오버헤드** | **1,058ms** | **말이 끝난 뒤 인식기가 확정하기까지** |

→ 보고할 값은 **확정 오버헤드 ≈ 1.06초**다. 변동의 97.7%가 발화 길이로 설명되므로
원시 p50/p95는 "얼마나 길게 말했나"를 재는 것에 가깝다.

**인식 정확도**: 5문장 전건 정확 인식(발화자 확인). 말이 꼬인 구간까지 들린 그대로 옮겨
적었다 — 표본은 작지만 오인식은 관측되지 않았다.

⚠️ **개인정보**: `[STT]` 로그에 인식된 발화 원문이 남는다(실측에서 실명이 기록됨).
평가 증빙 목적의 의도된 동작이지만([sttTelemetry.ts:12](../../apps/web/src/lib/sttTelemetry.ts:12) 주석),
시연 중 참관인 발화도 그대로 쌓이므로 운영 전환 시 노출 범위를 재검토해야 한다.

### 4.8 TTS 경로 — provider에 따라 음성 출처가 다르다 🟡

백엔드 설정만 보면 `elevenlabs_api_key`·`avatar_voice_id_female`이 비어 있지만,
**현재 운영 경로(musetalk)에서는 무관하다.** 릴레이가 텍스트를 그대로 코랩에 넘기고
**코랩이 TTS까지 수행**하기 때문이다([avatar/service.py:722](../../services/api/app/domains/avatar/service.py:722) 주석).
실사용 확인 결과 ElevenLabs 음성·여성 보이스 모두 정상 출력된다.

| provider | 음성 출처 | 실측 `[TTS]` 로그 |
|---|---|---|
| **musetalk** (현재) | **코랩** | 0건 — 백엔드 TTS 미사용 |
| fastapi / gradio (폴백) | 백엔드 `tts_service` | gtts 31건 |

⚠️ **폴백 시 음질이 급락한다.** 코랩이 끊겨 fastapi로 폴백되면 백엔드 TTS가 동작하는데,
`elevenlabs_api_key`가 비어 있어 **gTTS 기계음**이 나간다. 오늘 아바타 다운 시 실제로 그랬다
(합성 31건 전부 gtts). 시연 중 코랩이 끊기면 같은 일이 벌어지므로, 안전망으로
백엔드에도 ElevenLabs 키를 넣어두는 편이 좋다.

**9.2(CER·MCD)는 실제로 코랩 출력 음성을 대상으로 측정됐다**(§2.6) — 백엔드 TTS 설정을
보고 판단하면 안 된다는 점이 이 사례로 확인됐다. 백엔드 `elevenlabs_api_key`가 비어 있어도
운영 경로의 음성 품질은 CER 0.4~0.7%로 정상이다.
