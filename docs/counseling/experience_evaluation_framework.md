# 상담·체험 2단계 판단 프레임워크

작성일: 2026-07-21

이 문서는 "1:1 상담·설문에서 판단할 것"과 "직무체험에서 관찰할 것"을 완전히 분리해
정리한 설계 문서다. 코드 구현 문서가 아니라 **개념 설계**이며, 실제 구현 여부는
각 장 끝의 "현재 구현과의 관계"에 표시했다.

## 0. 전체 구조

```
1:1 상담·설문
= 사용자가 말한 선호·가치·환경·제약조건
→ 어떤 직무를 체험시킬지 1차 후보 선정

직무체험
= 실제로 보인 업무이해·질문·학습·수행 행동
→ 1차 추천을 검증하고 보정

최종 결과
= 하고 싶은 일 + 실제 체험 반응 + 현재 준비도
```

두 단계를 섞어서 하나의 "적성 점수"로 뭉치면 안 된다. 상담은 **선호(말)**, 체험은
**행동(관찰)**을 보는 것이라 판단 기준과 척도가 다르다.

---

## 1. 1:1 상담·설문에서 필요한 판단 기준

### 목적

1:1 상담에서는 사용자의 **현재 직무 실력을 평가하지 않는다.** 확인하는 것은:

> 어떤 활동을 좋아하고, 어떤 환경에서 일하고 싶으며, 무엇을 중요하게 생각하고,
> 현실적으로 어떤 조건이 있는가

경력이 전혀 없는 사람도 충분히 답할 수 있어야 한다.

### 상담에서 판단할 7개 영역

| 영역 | 보는 것 | 참고 개념 |
|---|---|---|
| ① 활동 흥미 | 어떤 활동에서 재미·몰입을 느끼는지 (자료비교/아이디어/사람돕기/설득/절차처리/도구현장) | RIASEC(고용24 직업선호도검사) |
| ② 직업가치 | 안정성/보상/성취/자율성/성장/기여/인정/균형/도전 중 무엇이 중요한지 | 고용24 직업가치관검사 |
| ③ 선호 업무방식 | 분석↔아이디어, 혼자↔협업, 절차↔자율, 속도↔정확성 등 | O*NET Work Styles |
| ④ 선호 업무환경 | 사무/현장/실험실/이동, 소음·시간압박·반복도·교대근무 등 | 고용24 직업정보 + O*NET Work Context |
| ⑤ 현실적 제약조건 | 지역/시간/소득/교육투자기간/자격증/신체조건/학력 — **적성과 분리해서 봄** | 고용24 구직준비도검사 |
| ⑥ 경험·현재 준비도 | 관련 경험·교육·도구사용·자격증 — 없으면 "적합도 낮음"이 아니라 "준비도 자료 부족"으로 처리 | 고용24 직업적성검사 (적성/흥미 분리 원칙) |
| ⑦ 학습·피드백 방식 | 새로운 걸 배울 때 접근법, 도움 요청 시점, 오류 수정 방식, 반복연습 지속력 | — |

질문은 직업명을 바로 묻지 않고 **활동을 묻는다** (예: "최근 시간 가는 줄 모르고 했던
일이 있었나요?" → "그 일에서 가장 재미있었던 부분은?").

⑤ 제약조건은 적성과 분리해서 이중으로 표기한다 — 예: 흥미는 높지만 4년 이상 추가
학업이 필요하면 "직무 흥미 적합도: 높음 / 현재 진입 가능성: 낮음 / 대안 경로: 보조직무·단계별 준비"로 나눈다.

### 상담 LLM의 역할 — 판정자가 아니라 증거 정리자

LLM이 대화를 읽고 바로 "사회형 85점, 마케팅 기획자 추천"처럼 확정하면 근거가 약하다.
LLM은 대화에서 **근거(evidence)를 구조화된 형태로 뽑는 역할**만 한다:

```json
{"dimension": "work_style", "evidence": "혼자 조용히 자료를 정리하는 활동을 선호함", "value": "independent_focus", "confidence": 0.82}
{"dimension": "work_style", "evidence": "반복적인 단순 입력 업무는 선호하지 않음", "value": "low_repetition_preference", "confidence": 0.88}
```

**규칙**:
- 한 문장만으로 성향 확정 금지
- 가능하면 서로 다른 질문에서 2회 이상 근거 확보
- 모순되는 답변이 나오면 추가 질문으로 확인 (예: "정해진 방식이 편하다"+"간섭받는 건 싫다" → "절차·목표는 명확하되 세부 수행방법은 자율적인 환경을 선호하시는 걸까요?")
- 경험 없음 = 낮은 점수가 아니라 **미확인**
- 모르는 항목을 임의로 추정하지 않음
- 직업명보다 활동·환경·가치 중심으로 질문

### 상담 결과 비교 대상 — 직무별 선호 기준표

상담 결과는 NCS 수행점수와 바로 비교하지 않고, 먼저 **직무별 선호 기준표**와
비교한다 (예: 데이터 분석가 = 분석활동 선호 매우중요·정확성 중요·혼자집중 비교적중요...).
기준표 자체는 고용24 직업선호도·직업가치관 + 고용24 직업정보 + NCS 직무별 수행업무 +
필요시 O*NET 보조자료 + 전문가 검토로 구성한다.

### 상담의 최종 출력 — 1차 후보 직무 3개 (체험 전)

각 후보마다: 근거(질문별 응답 인용) / 확인 필요 항목 / 현재 준비도(경험 없으면
"판단 불가"로 명시)를 함께 낸다.

### 현재 구현과의 관계 (2026-07-22 정정 — 팀장님 검증 자료로 교차확인 후 수정)

**데이터는 준비돼 있지만 라이브 상담 경로에는 연결되어 있지 않다.**
`data/counseling/dimension_definitions.json`(43개 축), `question_bank.json`(54개
질문), `evidence_rules.json`, `followup_rules.json`, `recommendation_gate_rules.json`,
`module_mapping.json`은 전부 존재하고 `app/content/counseling.py`에 로더 함수도 있지만,
**그 파일 자체의 docstring이 명시하듯** "지금은 avatar/system.md 렌더링에 안전 규칙
요약 문자열(`build_safety_notes`)을 주입하는 한 지점에서만 실제로 호출된다." 즉 실제
상담에 연결된 것은 `safety_rules.json`(단정 금지·가설 표현 원칙)뿐이고, 43개 축·질문
은행·근거신뢰도·후속질문규칙·다축게이트·모듈매핑은 **아직 어떤 라이브 코드에서도
호출되지 않는 미사용 자료**다.

실제 라이브 상담·추천 경로는 다음과 같이 훨씬 단순하다(코드로 확인):
- 사전 설문 35문항 → RIASEC 6유형 점수만 산출 (`consultation/survey.py`)
- 자유대화는 `avatar/system.md` 프롬프트가 "성향/관심사/강점/업무선호"를 넓게 파악
- 추천 시 LLM이 대화 전체에서 `competency_scores`(5개 역량, `data/evaluation/competencies.yaml`)를
  한 번에 추정 → `INTEREST_WEIGHT = 0.3`(`recommendation/service.py:31`)으로 **역량 추정
  70% + 설문 RIASEC 매칭 30%**를 합쳐 최종 스코어 계산
- 근거 없는 역량은 `NEUTRAL_SCORE = 50`(`recommendation/service.py:29`)으로 채워짐 —
  "미확인"이 아니라 중립 50점이 되어, 근거가 전혀 없어도 모든 직무에 중간 점수가 생기는
  구조

즉 이 문서의 1~3절(7개 영역, 증거추출형 LLM, 직무별 선호 기준표)은 **목표 설계**이고,
실제로 상담이 지금 하고 있는 일과는 상당한 격차가 있다. 출처 대조는
[source_registry.md](source_registry.md)에 SRC-WORK24-*, SRC-ONET-INTEREST-PROFILER,
SRC-NCS-*로 등록되어 있으나, 공식 문항 대조 수동 검수표(54개)는 아직 미완료 상태다.
자세한 배경은 [current_counseling_audit.md](current_counseling_audit.md) §9, §19 참고.

## 2. 직무체험에서 필요한 판단 기준

### 목적

체험 단계는 상담과 목적이 다르다. 여기서 보는 것은:

> 사용자가 말로 표현한 선호가 실제 체험 행동과도 어느 정도 맞는지

체험 흐름(현재 체험 구조 그대로 활용):

```
선임·사수 만남 → NPC 인사 → 업무 프로세스 학습 → 퀴즈 → 신입 업무 안내 → 미니게임 → 체험소감문
```

### 국면별 관찰 기준

**① 선임·사수와 만나고 NPC에게 인사**
일반적인 "사회성"을 판정하지 않는다. 보는 것은 **업무상 상호작용 행동** —
필요한 상대에게 말을 거는가 / 역할을 확인하는가 / 업무 관련 질문을 하는가 / 후속
질문을 하는가 / 이해 못한 부분을 재확인하는가. 판단 명칭도 "사회성 높음/낮음"이
아니라 "업무상 의사소통 행동 / 정보 요청 행동 / 경청 및 확인 행동"으로 붙인다.

**② NPC와 대화하며 업무 프로세스 학습**
담당 역할 구분 / 업무 목적 이해 / 순서 파악 / 정보 탐색 / 설명 충돌 시 재확인 여부를
본다. 자유대화만 열어두면 사용자마다 기회가 달라지므로, 각 시나리오에 **동일한
관찰 장치**가 있어야 한다 — 선임이 일부러 완료기한/결과물형식/보고대상/우선순위/
주의사항 중 하나를 빼고 설명하고, 사용자가 그걸 되묻는지 관찰한다.

**③ 간단한 퀴즈**
직무 적합도를 직접 평가하는 도구로 쓰면 안 된다(초보자는 당연히 지식이 없음). 보는
것은: 설명을 이해했는지 / 피드백을 읽었는지 / 재시도에서 개선됐는지 / 같은 실수를
반복하는지. 판정은 "현재 사전지식: 낮음 / 학습 적응·피드백 반영: 높음"처럼 두 축을
분리한다.

**④ NPC를 통해 신입 업무 확인**
업무 시작 전 무엇을 확인하는지 본다 — 목표/완료기준/마감시간/자료범위/우선순위/
보고대상/주의사항 확인 여부. 직업공통의 업무이해·의사소통·자기관리 행동과 연결.

**⑤ 신입 직무 미니게임**
순수 클릭속도·마우스 숙련도를 직무 적합도로 오해하면 안 된다. 낮은 비중: 클릭
속도, 손 떨림, 처음 조작 실수. 볼 것: 지시사항 확인 여부, 올바른 순서 수행, 정확성,
실수 발견·수정, 힌트 사용 시점, 재시도 향상도.

**⑥ 체험소감문**
"잘했다고 주장하는지"를 보는 게 아니라 다음을 추출한다 — 가장 재미있었던/부담스러웠던
활동, 어려웠던 이유, 다시 해보고 싶은 업무, 예상과 달랐던 부분, 잘했다고 느낀 부분,
더 배우고 싶은 부분. (예: "오류 찾는 건 재미있었는데 계속 확인받는 과정은 피곤했다" →
오류탐색 선호: 높음 / 반복적 대인조율 선호: 낮음)

### AI 코치의 역할 분리

AI 코치가 체험을 전부 혼자 판정하면 안 된다.

| 주체 | 담당 |
|---|---|
| **코드** | NPC 방문 여부, 대화 시작 여부, 질문 시점, 퀴즈 답변·재시도, 힌트 사용, 미니게임 성공/실패, 오류 수정, 소요시간 — **기록** |
| **LLM** | 질문의 목적 분류(기한 확인/완료기준 확인/후속질문 여부), 도움 요청의 적절성, 피드백 이해·수용 여부 — **분류** |
| **코드** | LLM이 붙인 행동 태그 + 게임 로그 + 퀴즈/미니게임 결과 → **점수 계산** |
| **LLM** | 왜 이런 결과가 나왔는지 사용자 언어로 **설명** |

즉 `AI 코치 = 관찰·분류·설명`, `코드 = 기록·규칙·점수 계산`으로 역할을 나눈다.

### 체험 결과 비교 대상

상담용 흥미표가 아니라 다음과 비교한다 — ① NCS 직업공통능력(의사소통/문제해결/
자기관리/대인관계/디지털/직업윤리/필요시 수리), ② 해당 직무의 NCS 수행내용(자료수집/
정보분석/고객요구파악/일정관리/결과보고/장비점검 등), ③ O*NET Work Activities·Work
Context 보조자료(문제해결과 의사결정/창의적 사고/타인과의 협력/업무환경과 자율성 등).

### 현재 구현과의 관계 (2026-07-22 정정 — 팀장님 검증 자료로 교차확인 후 수정)

이 장은 **신규 설계이며 아직 구현되어 있지 않다.** 실제 체험 채점은 다음처럼 동작한다(코드로 확인):

- NPC 대화는 LLM이 `trust`/`schedule_stability`/`requirement_clarity` 3개 상태값만
  올리고 내린다(`scoring/service.py`) — "기한을 확인했다", "후속질문을 했다" 같은
  **구체적 행동 태그는 남지 않고** 상태값 변화량만 남는다. NPC 호감도도 업무상
  정보확인 행동이 아니라 공손함·비속어·정답 대신 요청·발화 길이 등 **일반적인 말투
  측정에 가깝다.**
- 미션 점수 = 채점 점수 × 자력 보정(사용한 최고 힌트 레벨 기준). 힌트 배율은
  `SELF_RELIANCE = {0: 1.0, 1: 0.9, 2: 0.8, 3: 0.7}`(`scoring/aggregate.py:17`),
  본편 미션 80% + 돌발과제 20%(`MISSION_WEIGHT = 0.8`, 같은 파일:19). 이 구조는
  **"처음부터 알고 있던 사람"과 "도움 없이 스스로 푼 사람"에게 유리**하고, 이 절이
  중요하게 본 "첫 시도는 낮았지만 피드백을 반영해 개선했는가"는 별도 학습적응
  점수로 분리되어 있지 않다(재시도 로그는 남지만 최종 집계로 충분히 전달 안 됨).
- 미니게임은 정확도를 역량 점수에 25% 반영(`aggregate.py:26`)하는데, 시간·실수
  횟수는 기록되지만 "첫 시도 이후 학습" 여부와 "마우스 숙련도"를 분리해서 보지 않는다.
- 체험소감문은 채점 대상이 아니라 리포트 재료로만 쓰이는 게 현재 설계상 맞다
  (`simulation/service.py`) — 다만 재미·부담·재체험의향 등을 구조화 저장하지 않고
  최종 리포트 생성 시 LLM이 매번 자유롭게 해석한다.
- `data/evaluation/competencies.yaml`의 5개 역량(`situation_judgment`, `problem_solving`,
  `communication`, `collaboration`, `task_management`)은 이 절의 NCS 직업공통능력
  7영역(의사소통/문제해결/자기관리/대인관계/디지털/직업윤리/수리)과 **완전히 일치하지
  않는다** — 디지털·직업윤리·수리 대응 항목이 없음. 그대로 쓸지, 7영역으로 재정의할지
  결정 필요.
- 실제 시나리오 구조(`data/scenarios/*.yaml`)는 이 절이 말하는 "선임 만남→NPC 인사→
  프로세스학습→퀴즈→신입업무→미니게임→소감문" 6국면과 다른 형태다 — 실제로는
  `steps`(m1, m2...) 단위로 `type`(정상업무/자료·정보 누락/우선순위 충돌/오류·안전위험/
  보고·인계), `task.kind`(checklist/choice), `criteria`, `pass_score`, `hints`,
  `options`/`answer` 구조로 되어 있다. 이 절의 국면 관찰기준을 실제 step 구조에
  매핑하는 작업이 후속 과제로 필요하다(1:1 대응이 아니라 재해석이 필요할 수 있음).
- "코드가 기록할 것" 중 NPC 방문 여부·질문 시점·힌트 사용 등은 시뮬레이션 로그 테이블
  존재 여부부터 확인 필요(이 문서 작성 시점에 미확인).

## 3. 두 단계 최종 통합

```
상담·설문 결과 (사용자가 말한 것)      체험 결과 (사용자가 실제로 한 것)
├─ 흥미                              ├─ 업무정보 확인 (질문·경청)
├─ 가치                              ├─ 프로세스 이해
├─ 선호 업무방식                      ├─ 피드백 반영
├─ 선호 환경                          ├─ 업무 수행방식
└─ 현실 조건                          └─ 체험 후 선호
```

### 최종 결과 예시 (마케팅 기획 직무)

1. **선호 적합도: 높음** — 상담에서 아이디어 제안·고객 관점 활동 선호, 변화 있는
   업무환경 선호
2. **체험 행동 적합도: 중간** — 고객 요구 파악 질문은 잘함 / 여러 자료 우선순위
   정하는 과정에서 어려움
3. **학습 적응: 높음** — 퀴즈 첫 시도 후 피드백 반영해 결과 크게 향상
4. **현재 준비도: 낮음** — 관련 경험·도구 사용 경험 없음
5. **결론** — 현재 실무 준비는 부족하지만 기획 활동에 대한 흥미와 피드백 적응이
   확인되어 탐색을 계속할 가치가 있음

### 현재 구현과의 관계 (2026-07-22 정정 — 팀장님 검증 자료로 교차확인 후 수정)

이 4축(선호 적합도/체험 행동 적합도/학습 적응/현재 준비도) 구조는 **아직 어디에도
구현되어 있지 않다.** 현재 `Report` 스키마(`services/api/app/domains/reporting/schemas.py`)는
`fit_score`(단일 스칼라) + `strengths`/`improvements`/`advice` 평문 리스트 구조로, 이
4축 분리와는 형태가 다르다.

**정정**: 2026-07-21 리포트 기능 감사에서 "체험(simulation_id) → 리포트 연결 자체가
코드 경로에 없다"고 적었는데, 정확히는 **백엔드엔 이미 있다.** `reporting/service.py`가
`simulation_id: int | None` 파라미터를 받아 `final_fit = consult_fit * 0.5 +
performance["total"] * 0.5`(같은 파일:123)로 상담·체험을 50:50 병합하는 코드가 이미
존재한다. 끊긴 지점은 **프론트가 이 파라미터를 절대 채워서 보내지 않는다는 것** —
`apps/web/src/lib/api.ts`의 `createReport(consultationId: number)`가 `simulation_id`를
받는 파라미터 자체가 없고, 체험 완료 화면(`ScenarioGamePage.tsx`)도 완료 후 리포트
생성 API를 호출하지 않고 홈으로 돌아간다. 즉 **"체험 리포트 연동" 작업의 실체는 새
기능을 만드는 게 아니라, 이미 있는 백엔드 파라미터를 프론트에서 채워서 호출하도록
연결하는 배선(wiring) 작업**에 가깝다 — 이 문서의 4축 구조를 구현하려면 그 배선을
먼저 연결하고, 그 다음 병합 공식을 `fit_score` 단일값에서 4축 분리 구조로 확장해야 한다.
