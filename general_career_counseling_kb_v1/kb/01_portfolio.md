# 취업 포트폴리오 구성 가이드

> 포트폴리오는 작업물을 전부 모아두는 저장소가 아니라, 목표 직무에 필요한 역량을 증명하는 선별된 사례집이다.


## 1. 먼저 확인할 질문

상담자는 바로 목차부터 제시하지 말고 다음 정보를 짧게 확인한다.

- 목표 직무와 경력 단계는 무엇인가?
- 지원하려는 회사나 산업이 정해졌는가?
- 공개 가능한 프로젝트는 몇 개인가?
- 개인 프로젝트와 팀 프로젝트의 비중은 어떠한가?
- 링크, 화면, 코드, 문서, 수치 등 증거로 보여줄 수 있는 것은 무엇인가?

## 2. 기본 구성

### A. 소개

- 한 줄 직무 정체성
- 목표 직무
- 핵심 기술 또는 강점 3~5개
- 연락처와 이력서·깃허브·데모 링크

### B. 대표 프로젝트

프로젝트를 많이 나열하기보다 목표 직무와 가장 관련 높은 사례를 먼저 배치한다. 각 프로젝트는 아래 순서로 정리한다.

1. **문제와 배경**: 누구의 어떤 문제를 해결했는가?
2. **목표와 제약**: 일정, 데이터, 비용, 인력, 성능 등 어떤 조건이 있었는가?
3. **내 역할**: 팀 전체가 아니라 본인이 책임진 범위를 명확히 적는다.
4. **접근과 판단**: 무엇을 선택했고, 왜 그렇게 결정했는가?
5. **구현 또는 수행 과정**: 핵심 작업과 시행착오를 보여준다.
6. **결과와 증거**: 성능, 시간, 사용자 반응, 검증 결과, 전후 비교 등을 제시한다.
7. **회고와 다음 개선**: 한계와 후속 계획을 구체적으로 적는다.

### C. 보조 자료

- 기술 구조도
- 주요 화면
- 핵심 코드 또는 API 예시
- 테스트 및 평가 결과
- 발표 자료나 데모 영상
- 협업 방식과 본인 기여 범위

## 3. 프로젝트 설명 공식

**문제 → 내 책임 → 판단과 행동 → 검증된 결과 → 배운 점**

좋은 설명은 기술 이름보다 의사결정과 결과가 중심이다.

### 좋은 예시의 형태

> 응답 지연 때문에 시연이 불안정했다. 나는 백엔드 호출 구간을 측정하고 캐시 범위를 분리했다. 그 결과 반복 요청의 대기 시간을 줄였고, 실패 시 대체 경로가 동작하는지 테스트로 확인했다.

### 피해야 할 형태

> FastAPI, React, RAG, LLM을 사용한 프로젝트입니다.

기술 목록만으로는 지원자가 실제로 무엇을 했는지 알기 어렵다.

## 4. 팀 프로젝트 기여도 표현

- `팀에서 개발했다`보다 `내가 담당한 입력·출력·검증 범위`를 적는다.
- 다른 팀원의 성과를 자신의 결과처럼 표현하지 않는다.
- 본인 작업이 전체 흐름에 어떤 영향을 줬는지 연결한다.
- 커밋 수만으로 기여도를 증명하지 않는다. 산출물, 의사결정, 테스트, 장애 해결을 함께 제시한다.

## 5. 결과 수치 사용 원칙

- 확인 가능한 수치만 사용한다.
- 정확한 측정값이 없다면 수치를 만들어내지 않는다.
- 표본 수, 측정 환경, 기준을 함께 적는다.
- 전후 비교가 가능하면 같은 조건에서 비교한다.
- 결과가 기대보다 낮아도 원인과 개선 과정을 설명하면 좋은 사례가 될 수 있다.

## 6. 디지털 포트폴리오 체크리스트

- 첫 화면에서 목표 직무와 강점이 보이는가?
- 대표 프로젝트가 목표 직무와 직접 관련되는가?
- 각 프로젝트에서 내 역할과 결과가 분리되어 있는가?
- 링크와 영상이 실제로 열리는가?
- 모바일과 발표 화면에서도 읽을 수 있는가?
- 공개하면 안 되는 개인정보·고객정보·비밀자료가 없는가?
- 오탈자와 깨진 이미지가 없는가?
- 가장 강한 프로젝트가 앞에 있는가?

## 7. 상담 응답 규칙

- 사용자 자료를 보지 않고 “좋다” 또는 “부족하다”고 단정하지 않는다.
- 목표 직무가 없으면 먼저 직무를 좁히도록 돕는다.
- 프로젝트가 적다면 새로운 프로젝트부터 권하기 전에 기존 경험에서 증거를 추출한다.
- 최신 채용 트렌드나 특정 회사 선호 형식은 변동 정보이므로 현재 공고와 공식 채용 페이지를 확인하도록 안내한다.
